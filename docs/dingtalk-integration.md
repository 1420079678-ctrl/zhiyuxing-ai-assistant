# 钉钉集成与权限说明

这份说明用于回答一个在作品集展示里非常关键的问题：`这个项目如果放在钉钉里，别人是不是必须要有我的权限才能使用？`

## 结论

通常不是“必须拿到你的个人账号权限”，而是取决于应用类型和授权方式：

- 如果你做的是**企业内部应用**，它通常只在你所属的钉钉组织里可用。
- 如果你要让**其他企业或外部评审**使用，就不能只停留在单组织内部应用形态。
- 如果调用的是**组织级接口能力**，一般还会涉及管理员授权、应用授权或用户委托授权。

## 为什么作品集不建议只交付钉钉版本

对实习评审来说，最重要的是“能不能快速看到你的能力”。如果演示必须满足下面条件，体验会明显变差：

- 先加入你的钉钉组织；
- 再由管理员开通应用；
- 再完成组织或用户授权；
- 最后才能进入页面体验。

所以更适合作品集的做法是：

1. 提供一个独立 Web Demo，让评审在浏览器里直接体验核心流程。
2. 在 README 和文档里说明：项目真实落地场景支持钉钉集成。
3. 单独补充钉钉版本的接入方式、权限模型和部署边界。

## 钉钉场景下的常见权限分层

### 1. 企业内部应用

- 这类应用更适合组织内部使用。
- 应用通常与某个组织绑定，不适合直接拿给外部企业或面试官体验。
- 如果你的项目当前依赖企业内部应用能力，可以把它视为“真实部署场景”，而不是唯一演示入口。

### 2. 多组织分发或三方应用

- 如果你希望别的组织也能安装使用，就要走面向多组织的分发思路。
- 这时重点不再是“你把账号借给别人”，而是“别的组织是否安装并授权你的应用”。
- 从作品集角度看，这部分更适合作为架构与平台化能力说明。

### 3. 用户委托授权

- 某些能力是“应用已安装”之后，再由具体用户进行授权。
- 这更像是用户授予访问自己身份范围内的数据，而不是直接继承你的个人权限。

## 建议你在面试里怎么说

你可以直接这样表达：

> 这个项目真实设计目标是支持钉钉平台接入，但为了避免面试官必须进入我的钉钉组织，我额外提供了独立 Web Demo。这样既能展示核心能力，也能把平台权限边界解释清楚。

这样的说法会比“只能在我的钉钉里跑”更成熟，因为它体现了你考虑了：

- 可访问性；
- 权限隔离；
- 多租户分发问题；
- 作品集展示效率。

## 当前仓库采用的策略

- Web Demo 作为默认演示入口；
- 钉钉作为业务落地与平台集成场景保留在文档说明中；
- 不要求外部评审拥有你的组织权限或你的个人账号权限。
