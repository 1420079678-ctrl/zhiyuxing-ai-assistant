# 钉钉集成与权限说明

[中文](dingtalk-integration.md) | [English](dingtalk-integration.en.md)

这份说明用于回答项目部署中的一个关键问题：`如果把知愈星接入钉钉平台，使用方是否需要依赖某个个人账号或单一组织权限才能访问？`

## 结论

通常不是“必须拿到某个个人账号权限”，而是取决于应用类型和授权方式：

- 如果应用是**企业内部应用**，通常只在所属钉钉组织内可用。
- 如果目标是让**其他企业或外部团队**使用，就不能只停留在单组织内部应用形态。
- 如果调用的是**组织级接口能力**，一般还会涉及管理员授权、应用授权或用户委托授权。

对当前这个项目，更直白的理解是：

- 如果你现在做的是`钉钉企业内部应用`，那么别人通常**不能直接在钉钉里使用你的 AI 助手**。
- 他们一般需要先进入对应组织，或者该组织管理员已经安装并授权这个应用。
- 所以“钉钉版能不能给别人直接体验”这件事，答案通常是：**不能像 Web 页面那样直接公开访问**。

## 为什么项目不建议只保留钉钉入口

如果系统访问必须满足下面这些条件，项目的可用性和可维护性都会受到影响：

- 先加入特定钉钉组织；
- 再由管理员开通应用；
- 再完成组织或用户授权；
- 最后才能进入页面体验。

更稳妥的项目组织方式是：

1. 提供一个独立 Web 入口，保证服务本身可以直接运行和访问。
2. 在 README 和文档里说明：钉钉是可选的接入场景，而不是系统唯一入口。
3. 单独补充钉钉版本的接入方式、权限模型和部署边界。

## 钉钉场景下的常见权限分层

### 1. 企业内部应用

- 这类应用更适合组织内部使用。
- 应用通常与某个组织绑定，不适合作为唯一的对外访问入口。
- 如果别人不在这个组织里，通常就无法直接在钉钉端看到或使用该助手。
- 如果项目当前依赖企业内部应用能力，更适合将其视为“真实部署场景”，而不是服务的唯一运行形态。

### 2. 多组织分发或三方应用

- 如果目标是让其他组织也能安装使用，就要走面向多组织的分发思路。
- 这时重点不再是“借出个人账号”，而是“其他组织是否安装并授权该应用”。
- 从项目架构角度看，这部分更适合作为平台化与多租户能力设计。

### 3. 用户委托授权

- 某些能力是“应用已安装”之后，再由具体用户进行授权。
- 这更像是用户授予访问自己身份范围内的数据，而不是直接继承某个个人账号的权限。

## 当前仓库采用的策略

- Web 服务作为默认访问入口；
- 钉钉作为业务落地与平台集成场景保留在文档说明中；
- 不要求使用方拥有特定个人账号权限；
- 但如果是钉钉内部应用形态，使用方通常仍需要满足“属于该组织”或“该组织已安装授权”的前提；
- 如果后续接入组织级能力，再根据实际应用形态补充授权流程。

## 最适合对外说明的表达

可以直接这样描述这个项目：

- `Web 版`：可独立运行和访问，不依赖钉钉组织权限。
- `钉钉版`：属于可选集成场景；如果采用企业内部应用，通常只面向组织内成员，不是公开入口。
